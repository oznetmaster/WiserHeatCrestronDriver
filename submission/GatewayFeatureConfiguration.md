# Gateway feature configuration checks

Select `WiserHeatCrestronDriver.AndroidTests.GatewayUiTests.GatewayFeatureConfigurationsShowExpectedControlsAndRestoreOriginal` in the released runner's installed-test plan. It belongs to the opt-in Android control project and requires the normal processor/Android reservations, verified candidate and saved app endpoint. Set `AllowGatewayFeatureConfiguration` to true and provide the absolute private `ControlHubSettingsPath`. No managed room child is required for this gateway-only case. Keep credentials and actual bindings outside the repository.

The fixture reads the complete current gateway configuration and verifies that it identifies the independently queried physical hub. Missing, masked or incompatible settings cause refusal. It observes the initial Home options page, then cycles the `EnableWholeHouseHotWater` and `AllowAwayMode` settings through the other three combinations. The forward sequence changes one flag at a time. For each combination, it verifies the configured flags, ready processor feedback, visible status/button rows and absence of rows disabled by configuration. Visible rows must match current processor labels and enabled states. Navigation returns Home after each inspection.

Only these two driver configuration flags are written. The fixture sends no hub control commands. Independent hub reads check that schedules, guarded room policy, Away mode, hot-water overrides and other guarded system settings remain unchanged; naturally changing temperatures and scheduled output are not treated as configuration writes. Private evidence retains those before/after snapshots, configuration/instance fingerprints, requested flag transitions, processor observations and Android captures.

Two matching observations are required after each configuration request. Failed or uncertain requests are never repeated. A lost response is reconciled by reading the delivered state before restoring the original flags. Cleanup has its own cancellation deadline, so canceled or failed UI tests still attempt configuration restoration. Changed gateway identity, unrelated configuration or an unowned flag combination blocks automatic overwriting. Failed restoration keeps the result failed and the workflow's restoration marker unconfirmed for reconciliation. This is not rollback of hub settings: unexpected physical policy changes fail the test rather than authorize a write to the household hub.

The original flags and rendered Home page are verified at completion. Every variant must pass; a successful restoration cannot turn a failed inspection green. The fixture is prepared and builds, with synthetic coverage for all four starting combinations, uncertain replies, cancellation, evidence failures and foreign changes. It has not yet run on hardware.

This supplies the executable visibility/configuration cycle needed for the gateway's conditional Home controls. It does not inspect the Configure/Setup form's displayed labels or keyboard types, prove persistence across a processor reboot, test changed connection credentials, establish paired-instance isolation or measure command latency. Those retain their separate official-plan scopes. Run this after the immutable candidate's endurance period and reservation release, not while monitoring owns the processor.
